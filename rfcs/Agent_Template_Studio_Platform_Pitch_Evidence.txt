02. Every domain needs agents. The foundation should be shared.
The buyer is investing in reusable infrastructure. Each isolated agent project tends to repeat template/configuration work, model connections, service permissions and operational instrumentation. A common platform concentrates that effort into capabilities that domain teams can reuse. These are the intended economic benefits; no measured savings are asserted.

04. From template to registered agent in a few guided steps.
The few-click value applies once templates, models and domain connections are prepared. Choose the job, define the agent, choose its models and placement, grant appropriate data/context access, and save. AgentFactory validates and persists a configured instance. A saved agent is discoverable by its host application; creation itself does not provision a new model server or run inference. Avoid an exact click-count or elapsed-time claim because these have not been benchmarked.

05. Reuse the behavior. Configure it for the business.
The current catalog includes Anomaly Detection, General Query, Summarizer, Incident Report and Failure Investigation. 06. Managed or private models. One agent creation experience.
Give both deployment choices equal prominence. Managed models use configured hosted providers, including compatible-chat endpoints and Hugging Face. Private models can use an organization-operated compatible endpoint, Ollama, or the supplied vLLM/Ray serving path. The common model catalog/runtime lets domain teams select without building provider code per agent. Operator responsibility differs: provider credentials and service terms for managed; serving infrastructure, capacity and model operations for private. A catalog entry alone does not prove runtime support; do not name AWS Bedrock as working because its provider is not registered in the current factory. A private endpoint is not an air-gap guarantee: explicitly review every enabled decision-model, embedding and fallback path. vLLM AD selection blocks the Hugging Face backup; other private choices require that fallback to be disabled for private-only operation.

08. Connect domain data through approved services.
Explain catalog, attachment and authorization as a sequence. Domain APIs are registered with service details and supported operations. The agent configuration selects the APIs it needs. Runtime authorization checks domain, service state and granted business Read/Write permissions before supported actions execute. Transport POST does not inherently mean a write. Source systems retain ownership of business data. There is no generic arbitrary API execution or payroll write executor merely because a Write permission exists.

09. Give each agent only the access its task requires.
Anchor the secure-creation proposition in implemented controls: new agents receive no automatic service permissions; grants can be direct, through assigned roles, or through agent groups; same-domain restrictions apply; context reads are explicitly directional. Permissions are additive, so removing one grant does not revoke another grant path. Access is checked at execution and before restored/cached context can bypass revocation. Admin features use the configured shared admin key, not full enterprise identity or per-user SSO. These are concrete controls, not a security certification.

10. Compose agents without losing the access boundary.
Treat agent collaboration as a reusable platform primitive. A source publishes a trusted saved response; recipient discovery and transfer enforce permissions, domain and service scope. The receiving agent gets a versioned context snapshot, and the message/result is persisted. The implemented reference is AD-to-Incident Report. General Query can answer from permitted saved AD context even without payroll API Read. This demonstrates reuse of an existing result, not unrestricted autonomous orchestration or an arbitrary workflow designer.

11. One foundation. Domain-specific agents.
Make platform versus domain ownership clear. Platform teams supply the catalogs, runtime, supported model adapters, permission system, communication and operating views. Domain teams supply the business purpose, registered domain services/data, specialized rules or measurements, and host experience. The generic records adapter and Leaves example support reuse of anomaly/review/audit infrastructure. HR, Benefits and Insurance are opportunities rather than delivered end-to-end integrations. Domain provisioning and new component registration currently require trusted setup/code, not only UI clicks.

12. Manage agent readiness, quality and usage in one place.
The platform value continues after creation. The registry and My Agents organize saved agents; health checks validate selected model state, credential presence and limited service/context connectivity. Evaluation runs configured sample questions with reply checks. Metrics show usage, checks, incidents, latency, tokens and errors by agent/model. None of these constitutes independent certification; a green health badge does not establish successful inference or provider credits.

Summarize the business case around the platform. Templates and a guided form reduce repeated setup; central APIs and access controls make governance reusable; managed/private model support creates operating choice; common runtime and metrics reduce bespoke support.
